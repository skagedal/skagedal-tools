# pnpm without Corepack

Implements [#81](https://github.com/skagedal/skagedal-tools/issues/81).

Every Node project here runs on pnpm, and which pnpm is decided by
Corepack: the manifests carry `packageManager: "pnpm@10.33.0"`, and the
`pnpm` on `PATH` is Corepack's shim, which reads that field and fetches
the version it names. Both ends of that are going away. pnpm stopped
recommending Corepack with pnpm 11 — its installation page for 10.x is
the last to mention it, and a pnpm maintainer has said Corepack now
causes more problems for pnpm than it solves — and Node is dropping
Corepack from its distribution from Node 25. The Brewfile already says
as much, in its own way: `# brew "corepack" # Does not exist, not sure
how this should be installed now`.

pnpm has its own answer, which is to be installed like any other tool and
to manage its own version per project. This moves this repository to that,
and to pnpm 12 while it is at it, since 10.x is no longer maintained and
the version-management it relies on arrived in 11.

The adjacent repositories that follow the same conventions — today that
is `~/code/iggybilly` — take the same change, and it is written here once
rather than in each.

## Functionality

### On a machine

pnpm comes from Homebrew: `brew "pnpm"` in the dotfiles Brewfile, in
place of the commented-out Corepack line. Corepack is not installed and
nothing enables it. Running `pnpm` anywhere gives Homebrew's pnpm 12.

Homebrew's pnpm is a native executable from 12 onwards and does not
need Node to run, though the tools it builds still do.

### In a project

A project says which pnpm it wants the way pnpm now asks to be told, in
`devEngines`, as a range:

```json5
  devEngines: {
    packageManager: {
      name: "pnpm",
      version: "^12.4.1",
      onFail: "download",
    },
  },
```

The pnpm that runs checks the range. If it satisfies it, it carries on.
If not — an old Homebrew pnpm, a CI image a major version behind — it
downloads a version that does and hands over to it, and records exactly
which one in `pnpm-lock.yaml` under `packageManagerDependencies`, so the
next run on any machine uses the same one while it still satisfies the
range. That is what Corepack was for, done by pnpm itself, and it puts
the exact version where every other exact version already lives: in the
lockfile, with the manifest holding the range.

`onFail: "download"` rather than `"error"`, because an error sends the
person who hit it off to upgrade pnpm by hand, which is precisely the
chore the field exists to take away. The range is a caret on a full
version so that a machine with an older 12.x is upgraded rather than
trusted.

`packageManager` goes. pnpm refuses to use both fields and ignores
`packageManager` when `devEngines.packageManager` is present, so leaving
it in would be a second version number that nothing reads and everything
appears to.

### In CI

The workflow installs pnpm with `pnpm/action-setup` as now, asking for
major version 12. The project's own `devEngines` settles the exact
version from there, so the workflow never needs bumping for a minor
release.

### When pnpm is missing

`log-viewer`'s `web` feature builds a React app with pnpm, and its build
script tells you how to get pnpm when there is none. It says `corepack
enable && corepack prepare pnpm@latest --activate` today, which is
exactly what this change stops recommending. It will say `brew install
pnpm`, and point at pnpm's installation page for anywhere without
Homebrew.

## Implementation

### The manifests

In `linear-notifications/package.json5` and
`log-viewer/browser/package.json5`, `packageManager: "pnpm@10.33.0"` is
replaced by the `devEngines` block above. `iggybilly/web/package.json5`
takes the same change, and its comment — "an exact pin, because this one
says which pnpm runs rather than what it installs, and corepack verifies
it" — is replaced by one saying the range is resolved and pinned in the
lockfile.

`comparison-typescript-cli-arguments/package.json5` has no
`packageManager` today. It gets the `devEngines` block too, so that every
Node project in the repository pins pnpm the same way.

Before relying on it, confirm that pnpm reads `devEngines` out of a
`package.json5` rather than only a `package.json`: every manifest here is
JSON5, and a pnpm that silently skipped the field would run as whatever
version happened to be installed. `pnpm install` with a deliberately
unsatisfiable range, such as `^99`, settles it in one command — it should
fail to download rather than succeed.

### pnpm 12

Moving from 10 to 12 changes some things these projects touch:

- `pnpm-lock.yaml` is regenerated by `pnpm install` in each project, and
  gains the `packageManagerDependencies` section. Committed with the
  manifest change.
- pnpm 11 reads settings from `pnpm-workspace.yaml` and the global
  `~/.config/pnpm/config.yaml` only, not `.npmrc`. No project here has an
  `.npmrc`, so nothing moves.
- `allowBuilds` is already the form every `pnpm-workspace.yaml` uses.
- pnpm 11 defaults `minimumReleaseAge` to 1440 minutes. `AGENTS.md` asks
  for 4320, set explicitly, and the explicit setting still wins.
  `linear-notifications/pnpm-workspace.yaml` is missing it today and gets
  it in this change.
- pnpm 11 needs Node 22. CI runs 24 and Homebrew's `node` is 26.
- `install-node` in `shared.sh` finishes with `pnpm link --global`, which
  is how `linear-notifications` ends up on `PATH`. pnpm 11 reworked
  global installs, so run `./install linear-notifications` on the new
  pnpm and check that `linear-notifications` still resolves to the
  checkout. If `link --global` no longer does that, `pnpm add --global
  "file:$SCRIPT_DIR/$dir"` is the replacement to try.

### CI

In `.github/workflows/tests.yml`, the `pnpm/action-setup` step's
`version: 10` becomes `version: 12`. The same edit goes into
`iggybilly/.github/workflows/main.yml`, the one workflow there that sets
up pnpm.

### The build script hint

`log-viewer/build.rs`, in `require_pnpm`:

```rust
        "log-viewer's `web` feature needs pnpm on PATH to build the React app under browser/. \
         Install pnpm (`brew install pnpm`, or see https://pnpm.io/installation) and retry, \
         or build without the `web` feature.",
```

### AGENTS.md

The "Node.js Programs" section gains a rule after the one on
`minimumReleaseAge`:

```markdown
- Pin pnpm with `devEngines.packageManager` in `package.json5` — a caret
  range on a full version, with `onFail: "download"` — and never with the
  `packageManager` field. Do not use Corepack: pnpm no longer recommends
  it and Node no longer ships it. pnpm itself is installed from Homebrew.
```

### Outside this repository

- `~/code/dotfiles/Brewfile`: the commented `corepack` line becomes
  `brew "pnpm"`.
- On each machine, once: `npm uninstall --global corepack`, which removes
  the shim at `/opt/homebrew/bin/pnpm` so Homebrew's can link, then `brew
  install pnpm`. Check afterwards that `readlink "$(command -v pnpm)"` no
  longer mentions corepack.
- `~/code/iggybilly`: the manifest, lockfile and workflow changes above,
  as its own commit in its own repository.

## Open questions

- **Homebrew or pnpm's own installer.** pnpm's page leads with its
  standalone script and `pnpm self-update`. Homebrew is chosen here
  because everything else on these machines comes from the Brewfile and
  stays current with `brew upgrade`; the cost is that `pnpm self-update`
  must not be used, since it would fight Homebrew over the binary.
- **A floor on the range.** `^12.4.1` makes a machine with 12.0 download
  12.4.1 or later, which is the point, but also means the range needs a
  bump before anyone can depend on something newer. The alternative is
  `^12` and trusting whatever 12.x is installed.
- **Node itself.** The same `devEngines` object can declare a Node range,
  and pnpm can manage Node versions too. That would let `fnm` go from the
  Brewfile, but it is a separate decision and not part of this one.
